# ValueFlow: codebase, design, and product review

Reviewed September 12, 2026. This is an assessment and proposed roadmap; application code has not been changed.

## Assessment

ValueFlow has a compelling foundation: connect AI delivery to measurable outcomes, keep release gates tied to evidence, and make those facts accessible through a briefing and a proposal inbox. Its strongest assets are the pure domain package, shared request validation, explanation UI, restrained visual language, and meaningful integration tests.

The largest improvement opportunity is trust in the meaning of the data. The product currently blurs predicted and observed value, simulations and recorded measurements, readiness and actual deployment, and a model suggesting an action versus being authorized to take it. These distinctions matter more than adding another dashboard or agent.

Recommended direction: **an evidence-backed decision workspace for AI delivery**. The core journey should be: understand the current position → inspect supporting evidence → make a decision → record what happened → measure the outcome.

## Priority findings

### 1. Production static-file containment can be bypassed — P1

[`static.ts:11`](/Users/al/git/Exponential/packages/server/src/static.ts:11) checks `candidate.startsWith(root)`. A sibling such as `dist-private` passes the check for a root ending in `dist`. A request with an encoded parent-directory separator returned a synthetic file from that sibling with HTTP 200.

Use path-component containment, account for symlinks, and reject malformed encodings cleanly. Test sibling prefixes, encoded separators, symlink escapes, and missing assets. Exploit impact depends on what matching sibling files exist and whether the production handler is reachable; this is not unrestricted access to every filesystem path.

### 2. Model selection can redirect credentials and project context — P1

[`llm.ts:74`](/Users/al/git/Exponential/packages/server/src/llm.ts:74) accepts `model@base-url`; [`llm.ts:178`](/Users/al/git/Exponential/packages/server/src/llm.ts:178) supplies the same authorization header regardless of destination. Model strings can enter through agent configuration and scout requests. The stub reproduction confirmed that an unconfigured endpoint receives an authorization header.

Replace arbitrary URLs in model selections with server-configured provider IDs. Bind credentials to providers, validate permitted destinations and redirect behavior, and only let authorized administrators configure a provider. This also prevents project briefings from being sent to a destination merely because a model string names it.

The API itself has no application authentication or authorization in [`app.ts`](/Users/al/git/Exponential/packages/server/src/app.ts:521). That may be acceptable for a private local prototype, but shared deployment requires a clear identity boundary, permissions, and actor attribution. An external proxy was not assessed. A single editable workspace-user record cannot represent independent users and approval authority.

### 3. “Simulate” sliders modify authoritative measurements — P1

[`ValuePage.tsx:244`](/Users/al/git/Exponential/packages/web/src/pages/ValuePage.tsx:244) says “drag gate sliders to simulate eval results.” [`store.ts:233`](/Users/al/git/Exponential/packages/web/src/state/store.ts:233) persists those changes as manual readings. They become the latest readings and affect gates, value, releases, and briefs. Manual readings also bypass the activity event generated for eval readings in [`repo.ts:821`](/Users/al/git/Exponential/packages/server/src/repo.ts:821).

Create an explicit scenario mode with a persistent banner, reset/discard, baseline comparison, and no writes to production evidence. Separately offer “Record measurement,” with value, source, observation date, evidence, and reason. Manual measurements can be legitimate, but should be distinguishable from connected evals and subject to the chosen gate policy.

### 4. Readiness is treated as proof of shipment — P1

[`derive.ts:142`](/Users/al/git/Exponential/packages/domain/src/derive.ts:142) labels a release “Shipped” when all criteria pass and its planned month is current or past. It does not establish deployment. Zero criteria also counts as all met; the reproduction returned `Shipped` for an empty release.

Model planned date, gate readiness, and actual deployment separately. Add a deployment record with environment, timestamp, version, and evidence. A deployment should remain a historical fact if a later eval regresses; show “deployed, current gate failing” rather than erasing shipment. Empty criteria should be “Not configured,” unless someone records an explicit exemption. Update tests that currently encode the existing semantics.

### 5. “Realized value” is an estimate, and history changes retrospectively — P1/product decision

[`derive.ts:65`](/Users/al/git/Exponential/packages/domain/src/derive.ts:65) adds configured milestone impacts when milestones are shipped and clear gates. This establishes delivery eligibility, not an observed reduction in labor or processing time. Independent percentage contributions can overlap and add above 100%.

[`derive.ts:167`](/Users/al/git/Exponential/packages/domain/src/derive.ts:167) calculates prior burn-up points using current status, current thresholds, current readings, and planned month. Changing a threshold today can alter a historical chart. A delayed shipment is attributed to its planned month.

Distinguish forecast value, value eligible after delivery, and observed benefit. Record baseline workload, observation period, adoption, actual outcome, and attribution assumptions. Define whether milestone impacts are percentage points against one shared baseline or sequential reductions. Derive historical views from time-stamped facts and versioned gate definitions; the “derive, never store” principle remains useful, but current facts alone cannot reconstruct history.

### 6. Editing can lose drafts or overwrite newer evidence — P1/P2

[`store.ts:201`](/Users/al/git/Exponential/packages/web/src/state/store.ts:201) catches write errors without returning a failure to the editor. Several callers close immediately, including [`App.tsx:285`](/Users/al/git/Exponential/packages/web/src/App.tsx:285) and the Value page. A failed save therefore closes the dialog and loses the draft.

Whole-milestone saves also contain metric `current` values. [`repo.ts:870`](/Users/al/git/Exponential/packages/server/src/repo.ts:870) appends a manual reading when those differ from the latest database values. If an eval arrives while an editor is open, saving a name change can append the editor's stale values over the fresh eval.

Separate metadata updates from measurement ingestion. Return explicit mutation results, keep drafts open on failure, use field-level errors, disable duplicate submission, and introduce entity revisions for conflicts. Reconcile successful mutations using server-returned entities. Sequence metric writes and protect pending local edits from an unrelated full-state reload.

### 7. Budget ceilings are incomplete controls — P1 if relied upon

[`spend.ts:99`](/Users/al/git/Exponential/packages/domain/src/spend.ts:99) ignores zero-dollar and zero-token ceilings; both are accepted by the input schema. The reproduction returned budget state `none`. Preflight checks look at existing usage, with no reservation for an incoming call or concurrent calls.

Retry usage is overwritten by the final response in [`agents.ts:219`](/Users/al/git/Exponential/packages/server/src/agents.ts:219). Judge requests in [`evals.ts:148`](/Users/al/git/Exponential/packages/server/src/evals.ts:148) persist scores without recording their token usage in a billed-call ledger. Automatic curation, setup, and nested benchmark/scout calls need a consistent enforcement path.

Centralize provider calls behind a usage ledger. Record every attempt, judge, retry, provider, model, price version, and missing-usage state. Reserve capacity atomically before calls and reconcile afterward. Define zero as disabled or reject it; do not silently interpret it as unlimited. If strict dollar caps cannot be guaranteed, label the control as a spending alert/soft limit.

### 8. Autonomy and proposal acceptance need stronger boundaries — P1 for automatic writes

The UI describes earned autonomy, but the rules API accepts `auto: true` and [`agents.ts:259`](/Users/al/git/Exponential/packages/server/src/agents.ts:259) applies proposals based on that flag. The execution path does not enforce the UI's historical acceptance threshold. The model ties a proposal to a free-text rule; this is not a deterministic authorization policy.

Enforce action type, scope, allowed transitions, and maximum impact in application code. Require human decisions for approvals or shipment unless a narrowly defined trusted integration supplies the evidence. Count human acceptance separately from automatic acceptance so automation does not manufacture its own success signal.

[`proposals.ts:33`](/Users/al/git/Exponential/packages/server/src/proposals.ts:33) checks that the target exists but does not verify the state on which the proposal was based. Add an expected entity revision, expiry, a before/after preview, affected releases/value, and conflict handling. Apply the mutation and decision record in one transaction. Explicitly record who accepted and why.

### 9. Editor keyboard and screen-reader behavior is incomplete — P2

The target editor retained focus on the underlying “Edit targets” button when opened. Escape did not close it. [`Modal`](/Users/al/git/Exponential/packages/web/src/ui/primitives.tsx:275) does not manage initial focus, a focus trap, restoration, or Escape; the global handler closes only the palette and chat. [`Lbl`](/Users/al/git/Exponential/packages/web/src/ui/primitives.tsx:216) renders a `div`, leaving the target fields without associated labels in the accessibility tree.

Implement one tested dialog primitive with focus management, real labels, error descriptions, and unsaved-draft handling. Remove nested interactive controls from clickable milestone/release/portfolio rows. Provide keyboard equivalents and textual summaries for charts. This is a functional accessibility finding, not a claim of comprehensive standards testing.

### 10. Sync failures can look like empty successful data — P2

[`github.ts:145`](/Users/al/git/Exponential/packages/server/src/connectors/github.ts:145) turns failed check/review fetches into empty arrays, and workflow fetch failures into no builds. Sync replaces the previous project facts wholesale. A permissions failure or transient endpoint error can therefore erase visible information while the broader sync appears successful. PR/workflow limits and the three-page commit cap also produce partial views.

Track freshness, coverage, and errors per resource; preserve the last successful resource snapshot. Distinguish “none,” “unknown,” “stale,” and “partially fetched.” Add pagination or explicitly label the sampled window. Use incremental updates, conditional requests, bounded concurrency, and a per-project sync lock when scale warrants it.

### 11. Long jobs and scores overstate certainty — P2

Jobs are partly in process memory; server restart recovery and explicit terminal failures are missing. `startJob` logs a failure then sets `running: false`; the client can announce completion without knowing that the job failed. A seeded working run also produces “Active now: 1” while the UI says models are disabled.

Add persisted job states, errors, cancellation, leases, restart reconciliation, and idempotency. All execution entry points should share this service. Keep sample runs visibly marked and avoid seeding permanently running work.

Benchmarks use fixed case instructions against live project state and skip absent sample projects ([`evals.ts:178`](/Users/al/git/Exponential/packages/server/src/evals.ts:178)). Freeze case snapshots for comparable model/prompt evaluations, report skipped cases and sample counts, and test adversarial/stale/missing evidence. A number appearing somewhere in a briefing is a grounding heuristic, not proof that a claim is correct. Distinguish execution completion, judged quality, and independently verified correctness.

### 12. Some visualized data is assumed rather than recorded — P2

[`RoadmapTimeline.tsx:90`](/Users/al/git/Exponential/packages/web/src/charts/RoadmapTimeline.tsx:90) gives every milestone a start three months before its target, while the legend calls the bars “delivery windows.” Record actual planned starts or use target markers. `nextRelease` takes the first future entry rather than sorting chronologically and considering current overdue releases.

The burn-up chart's y-axis is based on the target rather than all plotted values, so large summed impacts can exceed its bounds. Derive the displayed range from the series and provide an explicit scale policy.

## Frontend design and user experience

Keep the dark palette, Inter typography, restrained color, compact navigation, keyboard shortcuts, and “Why this number?” explanations. These already form a coherent product. Improve hierarchy and interaction before introducing a new visual identity.

| Surface | Recommended change | User benefit |
| --- | --- | --- |
| Glance | Three prioritized decisions with owner, due date, consequence, and one action; expand evidence on demand | A briefing that can be acted on in a minute |
| Overview | Compact project summary, next release, expected/observed value, confidence, and next decision; collapse repeated briefing detail | Users reach the project's essentials without scrolling through a second Glance |
| Portfolio | Table/card toggle; filters for owner, stage, risk, blocked release, and stale evidence; saved views | Useful at 30 projects as well as three |
| Value | Explicit measured/scenario modes, units, baseline, evidence freshness, adoption and actual outcome | A credible value story rather than an attractive percentage |
| Roadmap | Near-term default, zoom, overdue section, blockers linked directly to the relevant control | Understand what can ship and what would unblock it |
| Governance | Required-before-release distinction, owner, due date, evidence and approval history | Completion percentages do not obscure one decisive missing approval |
| Inbox | Before/after preview, evidence, affected objects, approve/edit/delegate/snooze; batch only equivalent low-risk work | Review a decision rather than interpret an agent's instruction |
| Agents | Primary actions such as “Prepare update” and “Review delivery risks”; configuration, models, prompts and benchmarks in an administrative area | Users do not need to learn ten agent personalities to complete a task |
| Data | Move workspace identity and integrations into Settings; make Calendar accessible as a workflow | Remove the catch-all destination and improve discovery |

Glance currently repeats a finding in its sentence, explanation and embedded widget; “View release” and “open” can lead to the same place. Keep one concise claim, one recommended action, and expandable evidence. Rank by decision urgency, value affected, severity, and freshness—not only distance from a numeric gate. Being two percentage points short is not necessarily easier to fix than being six short.

On desktop, make actionable text more prominent than provenance and metadata. Use color consistently for distinct concepts: intrinsic risk tier, delivery state, and measurement confidence should not compete for the same meaning. The Roadmap can label a release “At risk” while showing a red diamond because color uses completion ratio and wording uses time; align or explicitly separate these signals.

At phone width, three KPI cards stack before the working content, navigation extends horizontally, and the SVG chart shrinks until its labels are extremely small. Use a compact summary strip, an explicit project switcher, an accessible tab overflow menu, and a milestone list as the default mobile roadmap. Keep chart text at readable sizes with deliberate scrolling or a reduced range. Choose larger touch targets for editing and triage.

## Product opportunities worth exploring

1. **Evidence-linked decisions.** Introduce a Decision object: question, owner, due date, options, recommendation, evidence references, affected release/value, and outcome. Both humans and agents can create it. The inbox becomes a shared operational workflow instead of only AI output review.
2. **A release evidence pack.** One exportable record containing the deployed version, gate readings and dataset versions, approvals, exceptions, decision history, and observed benefits. Historical reconstruction must precede claims that this is an audit-ready record.
3. **A genuine scenario planner.** Compare baseline with revised dates, gate outcomes, adoption and impact assumptions. Show which releases become ready and how the value forecast changes. Save named scenarios without changing authoritative facts.
4. **Benefit measurement after launch.** Track expected versus observed impact, adoption, error/rework rates and evidence confidence at 30/60/90-day review points. Support an explicit “benefit not yet measured” state.
5. **Typed metrics.** Support higher-is-better, lower-is-better and bounded-range measures with units. AI projects need latency, cost, error rate and task success as well as percentages. Add sample size, evaluation dataset, model/version and freshness policy.
6. **Dependency-aware planning.** Link milestones, approvals, shared services and release criteria. Explain the critical blocking chain and identify work that unblocks multiple releases. Add estimated dates/confidence only when underlying estimates exist.
7. **Guided setup from evidence.** Keep document setup, but distinguish extracted facts, assumptions and unanswered questions. Show source snippets beside each suggested field. Add PDF support when justified by actual onboarding inputs; start with a minimal project and recommend the next missing piece progressively.
8. **Outcome-oriented automation.** Prefer recurring workflows tied to a decision or deliverable over new agent names. Measure useful suggestions, time to decision, reversal rate and blocker resolution. Treat prompt tuning and model scouting as experiments with a stable evaluation set and rollback.

Useful product measures would be time to first evidence-linked milestone, time to identify the next blocker, time to resolve a decision, percentage of release criteria backed by current evidence, and percentage of shipped projects with observed benefit measurements. These measure the product's promised value more directly than run count.

## Codebase improvements

Preserve the modular monolith and SQLite unless measured needs justify a change. The domain/shared/server/web split is appropriate. Avoid a framework or database migration as the first response to complexity.

- Split the 1,072-line repository by domain and the HTTP router into focused route modules. Keep transactions visible at business-operation boundaries.
- Introduce services for proposal decisions, execution/usage, and evidence ingestion so API, scheduler, chat and setup cannot bypass the same rules.
- Keep `GET /api/state` as a bootstrap option, then add scoped queries and paginated run/event details. It currently assembles the entire workspace, and full reloads recur after many operations. Benchmark realistic portfolio and reading volumes before choosing caches or indexes.
- Standardize form validation with shared schemas, but add relational validation: ordered thresholds, unique nested IDs, real dates, allowed URL schemes, and valid references. Reversed base/stretch gates currently validate successfully.
- Use revisions and a documented mutation protocol rather than a global reload as the only rollback mechanism. Distinguish not-loaded, unknown and zero measurements.
- Add an error boundary, reconnect/freshness indicators, and a useful initial-load retry action.
- Preserve evidence when definitions are retired. Deleting metrics currently cascades their readings; append-only readings do not provide durable history if their parent can be removed. Use archival/versioning where audit history is a product requirement.
- Harden document extraction: compressed file limits do not bound decompressed content. Bound expansion size and entry counts, check source count before extraction, and move expensive parsing off the main request path. Prefer a maintained parser when support needs grow.
- Expand tests around meaningful failure modes: failed saves, stale edits, concurrent readings, proposal conflicts, authorization, provider routing, restart recovery, partial sync, deployment semantics, historical gates, and scenario isolation. Add a small browser suite for critical workflows and keyboard behavior; more snapshot tests alone would not catch the main issues above.
- Update documentation after semantics change. Current claims about simulation, immutable history, shipment, hard budgets and fixed benchmarks are stronger than the implementation supports. Separate demo mode from an empty production workspace.

## Suggested sequence

| Phase | Deliverable | Completion criterion |
| --- | --- | --- |
| 1: Contain and correct | File containment, provider-bound credentials, deployment identity decision, simulation isolation, zero-criteria/zero-budget fixes, safe form saves | Synthetic regressions pass; no simulated change affects real evidence; failed saves retain drafts |
| 2: Make evidence durable | Versioned metrics, explicit deployment facts, actor/revision-aware decisions, consistent usage accounting | A past release can be reconstructed and a stale proposal cannot overwrite newer state |
| 3: Simplify daily work | Decision-first Glance, focused Overview, portfolio filters, accessible dialogs, mobile summaries | Users can find a blocker and complete its next action with keyboard and phone layouts |
| 4: Expand differentiation | Observed benefits, scenario comparison, release packs, dependency planning | New features derive from trustworthy evidence and demonstrably shorten delivery decisions |

If only three initiatives fit the next cycle: **separate simulated from measured state, separate readiness from deployment, and make the decision workflow evidence-backed and safe to edit.** Address the two reproduced security issues alongside that work before exposing the application more broadly.
